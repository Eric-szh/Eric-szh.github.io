Personal project · Aug 2026 – present

Rhythm-Game Performance Lab

Python 3.13 · NumPy, pandas, SciPy, statsmodels, linearmodels, scikit-learn · ctypes (Win32 Raw Input) · pytest, uv

An end-to-end measurement and analysis system for my own rhythm-game play: hardware-level input capture, automatic song alignment, a statistical gate that every cross-song conclusion must pass, and targeted practice charts generated from the results. Most hypotheses I tested were refuted. The two that survived replicated on held-out data.

1. Problem

A PC taiko drum simulator scores a song and shows a summary. It does not give you per-note data: which hits were early, which were late, what happened right after a miss. If I wanted to know whether I was actually getting better, and at what, I had to collect the data myself, below the game.

2. Pipeline

  • Capture. A non-blocking Win32 Raw Input collector written in pure ctypes logs raw make/break events with a wall-clock and perf-counter anchor. Everything downstream, segmentation and note matching included, is a pure function of that log, so it can be recomputed offline whenever the analysis changes.
  • Firmware, from timing data alone. The drum controller emits a fixed 18 ms key pulse and suppresses the opposite zone for 15 ms. That explained why about 62% of two-handed "big notes" emit only one key, and ruled out a metric I had planned to use.
  • Identify and align. A coarse filter on hit count and duration narrows the candidate songs, then a 1 ms grid search over global offset picks the alignment that maximises hits inside the ±41.7 ms judgment window. I rejected dynamic time warping because it would absorb exactly the timing deviations I wanted to measure.
  • Practice charts. A procedural generator isolates one difficulty factor at a time and targets a 62–78% hit-rate learning band.

3. Making conclusions hard to fake

The first analyses treated every note as an independent sample. They were not. Notes within a session are correlated (ICC 0.103, design effect 23.4), so 5,890 notes were worth an effective sample of about 251. Every cross-song inference moved to session-level fixed effects with session-clustered standard errors.

Rules written in documents failed three times. So the rules became code. A gate() function returns one of three verdicts, holds, does not hold, or insufficient data. It refuses to run without a pre-registration card that names at least two competing explanations and fixed falsification criteria, and it stamps package versions into every result.

Review is done by a four-role agent workflow: coder, analyst, code QA, and a blind red team that sees the claim and the data but not the reasoning behind it. Given the reasoning, reviewers tend to agree with it. On day one the red team downgraded a finding by the gate's own author, which became a new "clean context" check in gate v2.

4. What held and what did not

Held, and replicated. Two findings passed the gate and then replicated on 34 held-out sessions:

  • Error clustering: an error raises the next note's error rate by 20.5 percentage points, in the same direction in 34 of 34 sessions. Held-out: 29 of 32 sessions, +22.0 pp, p = 3e−6.
  • Positive autocorrelation of timing deviation, 34 of 34 sessions in both the original and the held-out set.

Refuted.

  • A fatigue effect that looked strong at t = 4.03 fell to t = 0.20 once song identity was controlled. It was song-selection drift, not fatigue.
  • A planned two-handed "big note" metric, killed by the firmware's cross-zone suppression above.
  • Transfer from generated practice charts to a real song: a pre-registered transfer test did not show cross-day transfer, and it is reported as such.

5. Measuring progress

To track long-term improvement I needed one metric and a protocol. Variance decomposition showed that median absolute timing error is about 4.5 times more precise than hit rate, so that is the metric. A power analysis set the protocol at one session per week for 8 to 12 weeks on a frozen, hash-locked benchmark chart. The trend on that chart is not yet claimed as improvement: "practised the benchmark" has not been ruled out.

The codebase has 298 automated tests, a pinned environment, and every file-modifying tool defaults to dry-run.
